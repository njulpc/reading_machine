# 深度技术分析：Celty: SpMspV GPU Kernel and SIMT Co-Design for Efficient Dual-Sparse LLM Inference

## 1. 核心速览

**研究话题**：面向单用户 LLM 解码的双稀疏（dual-sparsity，权重稀疏+激活稀疏）推理加速，通过稀疏格式、GPU kernel 与 SIMT 微架构的协同设计高效支撑 Sparse Matrix–Sparse Vector（spMspV）工作负载。

**一句话总结**：Celty 提出 Run-Length Compressed CSC（RLC-CSC）稀疏格式与配套 GPU kernel，利用输入稀疏跳过权重列加载、用共享内存做散射累加；进一步提出 Celty Sparse SIMT Core，用流水线 RLC 解码器消除软件索引重建、用本地寄存器做无冲突累加；GPU kernel 较 cuBLAS 加速达 2.8×、较 Flash-LLM 达 2.4×，配合 Sparse SIMT Core 在 70% 双稀疏下较 cuBLAS 加速达 5.3×，端到端在 LLaMA-2-13B 上 60% 双稀疏下解码加速 2.63× 且 WikiText-2 困惑度 7.2（FP16 dense 为 4.9）。

---

## 2. 研究背景与动机 (Background & Motivation)

### 2.1 个人智能与单用户解码的双重瓶颈

LLM 部署于个人设备的愿景面临两个根本瓶颈：模型权重增大占用有限设备内存；自回归解码在单用户服务时受内存带宽限制。两者共同限制了可在数据中心外部署的模型规模与质量。稀疏性——移除部分权重——同时压缩内存占用与减少推理运算量，是自然的应对。

### 2.2 三类稀疏性的权衡

- **非结构化权重稀疏**（SparseGPT/Wanda）：按重要性移除单个权重，精度保持好但零模式不规则，需专用 kernel 加速，且在中等稀疏度下加速有限（如 Flash-LLM 在 70% 稀疏、4096×4096 层上仅比 cuBLAS 快 1.3×）。
- **结构化权重稀疏**（ShortGPT/BlockPruner/NVIDIA 2:4）：易加速但精度下降明显；2:4 半结构虽原生支持 tensor core，但固定结构仍损精度。
- **输入激活稀疏**（运行时幅度阈值化/SVD）：与权重稀疏互补，可在解码时跳过整列权重，精度损失小；但因模式输入相关，完整权重矩阵须常驻显存，无法减小模型体积。

### 2.3 双稀疏：理想但被忽视的工作负载

Dual-sparsity（DuoGPT）将激活稀疏与适度非结构化权重剪枝结合：权重稀疏压缩存储模型，激活稀疏驱动运行时加速，两者并存时每 token 需 fetch 的权重更少。这构成单用户解码的高效工作负载，形式化为 **Sparse Matrix–Sparse Vector（spMspV）** 乘法。

然而现有 spMspV kernel（用于 BFS 等图遍历）针对近 99% 稀疏设计，与 LLM 推理典型的中等稀疏（30–70%）不匹配；且多数 GPU 稀疏 kernel 工作针对 batched 多用户场景的 spMM，单用户解码（N=1）下 tensor core 计算过短无法掩盖解压开销。**没有先前工作研究中等双稀疏下的高效 GPU kernel 支持**——这正是 Celty 的切入点。

### 2.4 现有 kernel 在 N=1 下的失效

- **spMM kernel（load-sparse-compute-dense）**：稀疏数据载入寄存器，在 SMEM 中解压为 dense tile，用 tensor core 计算。大 N 时流水线可掩盖解压延迟，但 N=1 时 tensor core 计算过短，SMEM 流量开销无法隐藏。
- **spMV kernel**：避免该开销，在 SIMT core 上通过解压 kernel 散射加载输入并直接计算，但未针对双稀疏优化。

## 3. 核心方法与创新点 (Methodology & Innovations)

Celty 是格式-kernel-微架构的协同设计，分两层贡献。

### 3.1 RLC-CSC 稀疏格式

离线将权重打包为 **Run-Length Compressed CSC（RLC-CSC）** 格式，特点：

- 保持索引与非零值之间**严格一对一映射**，支持压缩列的向量化加载；
- 利用两种稀疏源跳过不必要的显存访问；
- 共享内存用于散射的部分积累加。

### 3.2 Celty spMspV GPU Kernel 设计

核心目标：利用输入稀疏跳过对应权重列的全局显存加载，减少显存流量与延迟。关键设计考量：

- **warp 内共享输入值**：若 warp 内 32 线程 fetch 不同输入值 $b$，非结构化输入稀疏会导致不同线程走不同控制流，产生 warp 发散抵消加速。因此所有 32 线程共享同一输入值 $b$，每个 warp 同时处理多行 $A$。
- **列跳过**：每次迭代 warp 加载 $b$ 并检查是否为零；若零，整个 warp 跳到下一列，不发起任何显存访问。
- **tile 划分**：每个 warp 分配覆盖 256 行（M）的 2D tile，迭代 64 列（K）。
- **SMEM 散射累加**：非零输入对应的压缩权重列被向量化加载，部分积在共享内存中散射累加。

该 kernel 单独较 cuBLAS 加速达 2.8×、较 Flash-LLM 达 2.4×。

### 3.3 性能剖析驱动的微架构协同

profiling 显示 kernel 约 **40% 执行时间**消耗在：(1) 从 RLC-CSC 重建行索引；(2) 散射累加时的共享内存 bank 冲突。这两者在 kernel 层面无法解决，驱动了微架构增强。

### 3.4 Celty Sparse SIMT Core 微架构增强

针对 SIMT core 的 CUDA core 流水线做轻量修改（而非 tensor core，因 N=1 是内存瓶颈）：

#### 寄存器式累加（Register-File-Based Accumulation）

将本地寄存器文件重用为无冲突的部分积缓冲，消除 SMEM bank 冲突。

#### 硬件 RLC 解码器（Hardware RLC Decoder）

集成三级流水线 RLC 解码器，在硬件中消除软件级索引重建开销。

#### 格式一致操作

直接操作同一 RLC-CSC 格式，**无需任何数据布局改变**——这是协同设计的关键：kernel 与微架构共享格式，避免格式转换开销。

面积开销 **<0.01%**，加速达：较 cuBLAS 5.3×（70% 双稀疏）、较 Coruscant 稀疏 tensor core 2.8×（单用户解码）。

### 3.5 端到端协同设计要点

- 离线：权重打包为 RLC-CSC（压缩索引）；
- 运行时：零值输入触发列跳过；非零输入加载压缩列并散射累加；
- 微架构：硬件解码+寄存器累加，消除 kernel 的两大瓶颈。

## 4. 实验设计与结果 (Experiments & Results)

### 4.1 实验设置

- **模型**：LLaMA-2-13B（端到端），以及代表性矩阵规模（如 4096×4096）。
- **稀疏度**：30–70% 双稀疏。
- **基线**：cuBLAS（dense）、Flash-LLM（稀疏）、Coruscant 稀疏 tensor core。
- **指标**：kernel 加速比、端到端解码加速、WikiText-2 困惑度。
- **场景**：单用户解码（N=1）。
- **会议**：ICCAD 2026。

### 4.2 Kernel 性能与分析

| 对比对象 | Celty GPU kernel 加速 |
|---|---|
| cuBLAS | 最高 2.8× |
| Flash-LLM | 最高 2.4× |

配合 Sparse SIMT Core：

| 对比对象 | 加速 |
|---|---|
| cuBLAS（70% 双稀疏） | 最高 5.3× |
| Coruscant 稀疏 tensor core（单用户解码） | 最高 2.8× |

### 4.3 端到端模型性能

LLaMA-2-13B 上 60% 双稀疏：

- 解码加速 **2.63×**（vs cuBLAS）；
- WikiText-2 困惑度 **7.2**（FP16 dense 为 4.9），在显著加速下保持合理质量。

### 4.4 消融研究

- 验证 RLC-CSC 格式相对标准 CSC 的加载效率增益；
- 验证列跳过（输入稀疏利用）的显存流量节省；
- 验证 Sparse SIMT Core 的硬件解码与寄存器累加各自贡献；
- 稀疏度扫描（30–70%）下的加速曲线。

## 5. 局限性与未来展望 (Limitations & Future Work)

### 5.1 局限性

- **需硬件修改才能拿到最高加速**：GPU kernel（2.8×）可在现有 GPU 部署，但 5.3× 的最高加速依赖 Sparse SIMT Core 微架构修改，这在商用 GPU 上短期内不可得，限制了最高性能的现实可用性。
- **单用户解码专精**：方法明确针对 N=1，在 batched 多用户场景（N≥8/2048）下相对现有 spMM/tensor core 方法的优势未验证，可能不利。
- **精度代价**：60% 双稀疏下困惑度从 4.9 升至 7.2，质量损失不可忽略；更高稀疏度下质量崩塌风险未充分讨论。
- **仅 LLaMA-2-13B 验证**：缺少 MoE、更大规模、其他架构（Mistral/Qwen）的端到端数据。
- **激活稀疏的获取**：依赖运行时幅度阈值化产生激活稀疏，该阈值与精度/稀疏的权衡未在本文深入（引用 DuoGPT），整体质量-速度链路的部分环节不在本文范围。
- **格式转换开销**：RLC-CSC 离线打包是一次性成本，但若权重动态更新（如在线剪枝/LoRA 适配）需重新打包，未讨论。

### 5.2 未来方向

- 探索在 batched 场景下 spMspV→spMM 的平滑过渡设计，使方法覆盖单用户到多用户。
- 与稀疏量化（如 4-bit 权重+稀疏）联合，进一步压缩模型体积与带宽。
- 研究自适应稀疏度：根据层/任务动态调整权重与激活稀疏比例，在质量-速度间寻优。
- 推动硬件厂商采纳 RLC-CSC 与 Sparse SIMT Core 思想，或在可编程硬件（FPGA/专用加速器）上原型验证。

## 6. 学术启发 (Takeaways for My Research)

### 6.1 软硬件协同设计的范式

Celty 最深刻的启示是：**当 kernel profiling 显示瓶颈无法在软件层解决时，应向上追溯到微架构协同设计**。40% 时间耗在索引重建与 bank 冲突——前者用硬件解码器、后者用寄存器累加，且共享同一格式避免转换。这启示我在做稀疏/量化加速研究时，不应止步于 kernel，而要识别"哪些瓶颈是软件不可解的"，并设计与之匹配的格式与微架构。

### 6.2 工作负载特征驱动的 kernel 设计

"warp 内共享输入值以避免发散""零输入整 warp 跳列"等设计，完全由 spMspV 工作负载特征（两稀疏源交集的不规则性、N=1 的内存瓶颈）驱动。这启示我：kernel 设计应从工作负载的特征分析出发，而非套用通用模板。我应先做特征剖析（稀疏分布、访存模式、计算/访存比），再定制数据布局与调度。

### 6.3 双稀疏是单用户 LLM 部署的有前景方向

权重稀疏（压体积）+ 激活稀疏（驱动加速）的组合，比单一稀疏更适合个人设备部署。这与 F-WANDA（仅权重稀疏）形成互补。在我的研究中，可考虑将 F-WANDA 式高质量权重剪枝与运行时激活稀疏联合，并用 Celty 式 kernel 兑现加速。

### 6.4 格式一致性原则

kernel 与微架构共享 RLC-CSC 格式、零布局转换，是协同设计的关键。这启示我：在设计压缩格式时，应保证从训练→剪枝→量化→部署的全链路格式一致，避免每环节的格式转换开销侵蚀收益。

### 6.5 诚实报告精度代价

论文诚实报告了 7.2 vs 4.9 的困惑度代价，未夸大。这启示我在加速研究中，应同等重视精度报告，避免只谈加速比而隐瞒质量损失，并用困惑度/下游任务精度完整刻画权衡。

### 6.6 与我研究的结合点

若我研究 LLM 推理加速，可借鉴：(1) 用 profiling 定位 kernel 瓶颈再决定是否需微架构协同；(2) warp 级跳过与 SMEM 散射累加的工程技巧；(3) 双稀疏框架下，我的剪枝方法应产出对 spMspV kernel 友好的稀疏模式（如列对齐），而非纯任意的非结构化稀疏。
