- 作者: Wanshun Su, Yang Shi, Feihu Liu, Ziwen Yu, Yan Min, Zhuoran Zhang, Qixun Wang, Haotian Wang, Shixuan Liu, Yuanxing Zhang, Peng Wu, Chengfu Huo, Liang Ding

## 1. 核心速览

### 1.1 研究主题

本文研究全模态大语言模型（Omni-LLMs，即同时处理音频和视觉模态的大语言模型）的 token 压缩问题。核心主题是一种无需训练的统一 token 压缩框架 OmniPack，它在 LLM 前进行结构性压缩、在 LLM 内进行任务相关语义精炼，通过模态特定重要性、全局覆盖、相似性感知合并以及文本引导的音视协作实现跨模态协同压缩。

### 1.2 一句话总结

论文提出 OmniPack 训练无关框架，在 LLM 前通过模态特定重要性、全局覆盖与相似性合并消除结构冗余，在 LLM 内通过文本引导与音视协作精炼任务相关表征，在 Qwen2.5-Omni-7B 上保留 98.0% 原始性能同时将 FLOPs 降至 16.7%，在仅 6.8% FLOPs 下仍保留 92.9% 性能。

## 2. 研究背景与动机 (Background & Motivation)

全模态大语言模型（Omni-modal Large Language Models, Omni-LLMs）在音视频理解任务上取得了卓越性能，能够同时处理音频和视觉信息，实现真正的多模态感知。然而，处理长且高度冗余的视觉和音频 token 序列带来了巨大的计算开销，这对高效部署提出了严峻挑战，迫切需要进行激进的 token 压缩。

**Omni-LLM 的冗余来源是多模态叠加的。** 与单模态或双模态（如视觉-语言）模型不同，Omni-LLM 同时处理音频和视觉两种非文本模态，两者的 token 序列都长且高度冗余。一段视频产生大量视觉 token（逐帧编码），同时其音轨产生大量音频 token（逐段编码），两者叠加使 token 总量急剧膨胀。对这种"双模态冗余叠加"进行有效压缩是 Omni-LLM 部署的独特挑战。

**现有方法在低 token 预算下的退化。** 论文指出，现有 token 压缩方法在低 token 预算（即激进压缩）下性能显著退化。论文将现有方法分为两类并分别分析其局限：

1. **LLM 前压缩（pre-LLM compression）的局限**：这类方法在 token 进入 LLM 之前就进行压缩（如视觉编码器后、音频编码器后）。其问题是可能在早期就丢弃结构上重要且全局分布的证据。因为在 LLM 前阶段，模型尚未理解任务需求，无法判断哪些 token 对当前任务关键，只能基于通用的显著性/冗余度进行剪枝，容易误删对特定任务重要的全局分布信息。

2. **LLM 内压缩（inner-LLM compression）的局限**：这类方法在 LLM 内部层之间进行 token 剪枝/合并。虽然此时模型已有一定任务理解，但现有方法往往**未能充分利用查询条件下的音视协作（query-conditioned audio-visual collaboration）**。即音频和视觉模态之间的互补信息未被联合利用来指导压缩——一个模态可能提供线索表明另一个模态的哪些 token 重要，但现有方法各自独立压缩，错失了这种跨模态协作机会。

**两类方法割裂的不足。** 此外，现有工作往往要么只做 LLM 前压缩、要么只做 LLM 内压缩，未能将两个阶段协同设计。LLM 前压缩适合去除结构性冗余（帧间重复、音频静音段），LLM 内压缩适合基于任务理解精炼语义。两者各有优势但互补，割裂使用无法实现最优压缩。

论文的动机由此明确：需要一种（1）统一协调 LLM 前结构性压缩与 LLM 内语义精炼的、（2）充分利用查询条件下音视跨模态协作的、（3）在低预算下仍保持高性能的训练无关 token 压缩框架。

## 3. 核心方法与创新点 (Methodology & Innovations)

OmniPack 是一个训练无关（training-free）框架，其核心设计在于协调 LLM 前与 LLM 内两阶段压缩，并充分利用音视跨模态协作：

**1. LLM 前：结构性冗余消除**

在 token 进入 LLM 之前，OmniPack 通过三重机制去除结构性冗余：

- **模态特定重要性（modality-specific importance）**：对视觉和音频两种模态分别评估 token 重要性。不同模态的冗余模式不同——视觉冗余主要来自帧间重复和背景区域，音频冗余主要来自静音段和重复声学模式。模态特定的重要性评估避免了用统一标准衡量不同模态的不适配。
- **全局覆盖（global coverage）**：在按重要性选择 token 时，保证全局覆盖——确保保留的 token 在时序和空间上分布广泛，避免某区域被完全清空导致信息盲区。这与 GSTEP 中的"密度-覆盖度平衡"理念类似，但此处应用于 Omni-LLM 的双模态场景。
- **相似性感知合并（similarity-aware merging）**：对于高度相似的 token，不是简单丢弃，而是进行合并（merging）。合并保留了信息内容（通过加权平均或类似方式），比纯丢弃更温和，在低预算下能更好地保持信息完整性。这一点对于"激进压缩但保性能"的目标尤为关键——合并使得即使 token 数大幅减少，信息也被浓缩而非丢失。

**2. LLM 内：任务相关语义精炼**

在经过 LLM 前压缩后的 token 进入 LLM 并经过充分的多模态交互后，OmniPack 进一步进行第二轮压缩：

- **文本引导（textual guidance）**：利用 LLM 中已形成的文本表征（来自用户查询或已生成的文本）来指导 token 精炼。文本查询天然指示了任务需要什么信息，因此可以用文本对视觉/音频 token 的相关性进行重新评估，保留与任务最相关的 token。这是对 LLM 前通用压缩的"任务感知"补充。
- **音视协作（audio-visual collaboration）**：这是 OmniPack 最具创新性的设计。在 LLM 内部，音频和视觉 token 已发生跨模态交互。OmniPack 利用一个模态的信息来辅助判断另一个模态 token 的重要性。例如，如果音频中检测到说话声，那么对应的视觉帧中人脸区域的 token 应被优先保留；如果视觉中检测到运动，对应时段的音频 token 也应保留。这种跨模态协作使得压缩决策比单模态独立压缩更精准。
- **多样化、任务相关表征的整合**：综合文本引导和音视协作，OmniPack 在 LLM 内精炼出多样化且任务相关的表征——既覆盖不同信息维度（多样性），又聚焦任务需求（相关性）。

**3. 两阶段协同设计**

OmniPack 的关键创新在于两阶段的协同：LLM 前压缩去除"不需要任务理解就能识别的"结构性冗余（重复、静音），为 LLM 减轻负担；LLM 内压缩利用"需要任务理解和跨模态交互才能识别的"语义相关性进行精炼。两阶段递进，各自发挥优势，形成从粗到细的压缩流水线。

**4. 训练无关**

整个框架不需要任何训练或微调，完全基于推理时的 token 选择与合并操作，可直接应用于任何已训练的 Omni-LLM。

## 4. 实验设计与结果 (Experiments & Results)

论文进行了广泛的实验验证：

**基准与骨干模型**：
- 在 **5 个基准**上进行评估。
- 使用 **3 个 Omni-LLM 骨干**进行测试，验证方法的跨模型泛化性。

**核心性能-效率结果**：

在 **Qwen2.5-Omni-7B** 上的结果尤为突出：
- 保留 **98.0% 的原始性能**，同时将 FLOPs 降至 **16.7%**。即在仅使用约 1/6 计算量的情况下，几乎完全保持性能。
- 在更激进的设置下，仅保留 **6.8% 的 FLOPs**（即削减了 93.2% 的计算量），仍保留了 **92.9% 的原始性能**。这是非常惊人的结果——在接近 15 倍计算压缩下仅损失约 7 个百分点性能。

**对比结果**：
- 在多种保留比例下，OmniPack **持续实现最佳的性能-效率权衡**，**超越了所有现有方法**。这一结论在 5 个基准和 3 个骨干模型上一致成立，验证了方法的有效性和泛化性。

**关键观察**：
- 两个极端设置的结果揭示了 OmniPack 的优势：在高预算（16.7% FLOPs）下接近无损（98.0%），在极低预算（6.8% FLOPs）下仍保持高保真（92.9%）。这表明两阶段协同设计在不同压缩力度下都能有效工作——LLM 前合并保证信息完整性（高预算下无损），LLM 内精炼保证任务相关性（低预算下仍保关键信息）。

## 5. 局限性与未来展望 (Limitations & Future Work)

**两阶段压缩的累积开销**：虽然压缩减少了 LLM 计算量，但 LLM 前的重要性评估、覆盖计算、相似性合并以及 LLM 内的文本引导和音视协作评估都引入了额外计算。在极端低预算下，这些压缩操作本身的开销占比可能上升，需要确保其远小于节省的 LLM 计算量。

**模态特定设计的扩展性**：当前框架针对音频+视觉双模态设计。若 Omni-LLM 扩展到更多模态（如触觉、嗅觉、3D 点云），模态特定重要性评估和跨模态协作的复杂度将组合爆炸，需要更可扩展的协作机制。

**合并策略的信息损失**：相似性感知合并虽然比丢弃温和，但合并不可避免地引入信息损失（多个 token 合并为一个时丢失细节）。对于需要精细空间或时间分辨率的任务（如精确的空间定位、精确的时间对齐），合并可能损害精度。

**文本引导的循环依赖**：LLM 内的文本引导依赖已形成的文本表征，但文本表征本身又依赖输入的视觉/音频 token。在自回归生成过程中，早期 token 的压缩决策影响后续文本表征质量，进而影响后续压缩决策，存在循环依赖。

**未来展望**：可探索学习型合并（而非固定合并策略）以自适应不同输入；研究流式 Omni-LLM 的在线两阶段压缩；将框架与量化联合实现多级压缩；探索三阶段或更细粒度的压缩流水线；研究在多租户场景下的压缩策略共享。

## 6. 学术启发 (Takeaways for My Research)

**"前+内"两阶段协同压缩范式**：OmniPack 将压缩分为 LLM 前（结构性）和 LLM 内（语义性）两阶段协同，是一种优雅的"粗筛+精炼"范式。这可迁移到：KV cache 压缩中先用通用显著性预剪再用查询相关性精剪；检索中先用嵌入相似度粗筛再用交叉编码器精排；数据管道中先用规则去重再学习去噪。关键启示是：不同压缩阶段适合不同信息——结构性冗余不需要任务理解，语义性压缩需要任务理解，应分层处理。

**跨模态协作指导压缩**：利用一个模态辅助判断另一个模态 token 重要性，是 Omni-LLM 场景下的独特洞见。这种"跨模态互相验证重要性"的思路可迁移到：多视角融合中用一个视角验证另一视角的关键区域；多模态检索中用文本模态指导视觉模态的索引构建；多传感器融合中用一个传感器的时间戳对齐另一传感器的关键帧。

**合并优于丢弃**：在激进压缩场景下，相似 token 合并比丢弃更温和、信息损失更小。这一原则在低预算场景下尤为关键——合并保留了信息的"质心"，而丢弃可能丢失关键信息。可在自己的压缩/采样工作中优先考虑合并策略。

**训练无关的工程价值**：OmniPack 的训练无关特性使其可即插即用，与 SlimVLM（训练感知）形成互补。这启示我：在研究压缩方法时，可先验证训练无关版本能否达到可接受性能（快速验证+易部署），再考虑训练增强是否值得额外成本。

**极端压缩下的性能保持**：6.8% FLOPs 下保持 92.9% 性能的结果令人瞩目，说明冗余远比想象的大。这激励我在自己的研究中探索"到底能压缩到什么程度"的极限，而非保守地停留在中等压缩率。
